# Research: Область поиска дублей

## R-1. Где хранить переключатель и область

- **Decision**: два ключа `setting`: `dupes_enabled` (`1` / нет ключа) и `dupes_scope` (`deck` / `all`, нет ключа =
  `deck`). Оба в `USER_KEYS`, пишутся `set_setting_cmd`.
- **Rationale**: так же устроен `hints_enabled`; область помнится, когда поиск выключают и включают снова (FR-002 —
  «Внутри колоды» по умолчанию только для первого раза). Старые базы ключей не имеют → поиск выключен (Assumptions).
- **Alternatives**: один ключ `off/deck/all` — теряется выбранная область при выключении; настройка на колоду —
  отвергнута в clarify.

## R-2. Набор поиска — одна функция

- **Decision**: `dupes::Scope` = `Off | Deck | All | Search(SearchSpec)`; `Scope::current(conn)`: если в `dupe_search`
  `state = running|done` — `Search`, иначе по настройкам. `scope_files(conn, &scope)` заменяет `files()` везде:
  `next_file`, `printed`, `refresh_exact`, `Index::load`, `groups`, `dupes_for`.
- **Rationale**: сейчас `files()` = колода + все стопки и вызывается из пяти мест; одна точка решает FR-005–FR-007,
  FR-013, FR-019. Плашки (`dupes_for`) берут набор колоды (`Deck`/`All`), даже когда открыт отдельный поиск (clarify).
- **Alternatives**: колонка `scope` в `dupe` — пары не принадлежат области, область — фильтр над ними; хранить пары
  по поиску — лишняя схема, повтор поиска и так быстрый (отпечатки остаются).

## R-3. Фильтр групп по набору

- **Decision**: `groups(conn, scope)` берёт пары, у которых **оба** файла в наборе; набор — `HashSet` путей в нижнем
  регистре. Сужение области («Колода и стол» → «Внутри колоды») мгновенно прячет группы со стопками (US2-4) без
  пересчёта. Выключенный поиск → `groups` пуст, экран показывает состояние «выключен», а не «нет групп».
- **Rationale**: таблица `dupe` хранит всё, что когда-либо найдено; набор решает, что показывать.

## R-4. Отдельный поиск

- **Decision**: `dupe_search` = `{"piles": [имя…], "deck": bool, "folders": [путь…], "state": "running"|"done"|"cancelled",
  "skipped": [путь…]}`. Обход внешних папок — тот же `walk()` (скрытые/системные и `.`/`$`/`@` пропускаются, FR-017);
  папка, вложенная в другую папку состава, в стопку или колоду, отбрасывается; файлы — по пути без регистра один раз.
  Недоступная папка (`read_dir` ошибка, нет диска) — в `skipped`, остальные ищутся (FR-021). `search_clear` удаляет
  ключ (закрыть итоги / отмена Esc); `search_start` перезаписывает (новый поиск заменяет итоги).
- **Rationale**: «разовый сеанс, не отслеживается» — JSON в настройке достаточно; цикл разбора читает его своим
  соединением. Переживает перезапуск приложения — не мешает: итоги видны до «Закрыть результаты».
- **Alternatives**: состояние в `AppState` (Mutex) — поток разбора живёт на своём соединении, пришлось бы протаскивать
  ещё один Arc; таблица `search_root` — лишняя схема.

## R-5. «Убрать копию» во внешней папке

- **Decision**: без новой логики: `moves::trash_copies` уже отправляет пути вне колоды списком `files` в
  `move_with` (журнал до хода, `safe_rename` между дисками). Тест: файл во временной «внешней» папке → ход в
  «Корзину» → `undo_last` возвращает под тем же именем. «Заменить» во внешней группе — только если лучшая копия в
  колоде (Assumptions), иначе кнопка скрыта.
- **Rationale**: принцип I уже реализован общим ходом; новый код — только место `"folder"` у копии.

## R-6. Скорость этапа «Дубли» (замер — первая задача, FR-024)

- **Гипотезы до замера** (по коду):
  1. `next_file` на каждый файл заново строит `files()` (чтение каталога колоды 5 000 записей + обход стопок) и
     грузит всю таблицу `fingerprint` — O(N²) на проход.
  2. `refresh_exact` стартует в первой итерации цикла (`dupes_at` = −60 с) и считает SHA-256 всех файлов одного
     размера до кадров — «первые 1–2 минуты кадры стоят» (FR-022).
  3. `Index::load` берёт все отпечатки базы, включая файлы прошлых колод вне набора, — лишние сравнения.
  4. Съём отпечатка (MF-декод + DINOv2) идёт в одном потоке, пока процессор и видеокарта простаивают.
- **Замер**: bench-тест `#[ignore]` в `develop.rs` на копии базы `big`: время по фазам на 200 файлах (список, SHA,
  `print::print`, `embed`, `compare`), и полное время этапа в dev с зондом подвисаний. Итог вписывается сюда до
  оптимизации.
- **Замер до** (2026-10-02, `bench_dupes_stage`, release, `big` + `big-table`, 5 000 файлов, DirectML): `files()` —
  10 мс; 200 видео за 167,6 с = **838 мс на файл**: `next_file` 17,5 · `print::print` (MF-декод) **530** · `embed`
  (DINOv2) **216** · `save_print` **72** (fsync на каждый файл, `synchronous=FULL`) · сравнение 2,4. `exact_pairs`
  (SHA-256 всех файлов одного размера) — **73 с** (26 796 пар — жёсткие ссылки стенда). Прогноз этапа на `big`:
  2 053 видео × 0,84 с ≈ 29 мин + фото + 73 с SHA в начале разбора.
- **Вывод**: гипотеза 1 мелкая (2 %), 2 подтверждена (73 с SHA до кадров), 3 — 0,3 %; главное — однопоточный декод
  (63 %), DINOv2 (26 %) и запись по одному файлу (9 %).
- **Decision (после замера, порядок)**: декод отпечатков в `workers()` потоков; `embed` пачкой из нескольких файлов;
  запись отпечатков транзакцией на пачку; SHA — после кадров и только по набору; кроме того, список файлов прохода строится один раз и обновляется при `PRAGMA data_version`;
  SHA — только на этапе «Дубли» и только для файлов набора; индекс — по набору; съём отпечатков в `workers()` потоков
  с пониженным приоритетом (декод параллельно, `embed` и `compare` — в потоке цикла, порядок записей сохраняется).
- **Alternatives**: отдельная служба/процесс — избыточно; GPU-декод уже включён (`mf::hardware`).
- **Замер после** (2026-10-04, release, DirectML, 4 потока):
  - `bench_printer` (тот же порядок файлов, 200 видео, область «колода и стол»): **354 мс на файл**, самая долгая пачка
    2,6 с. Старый `bench_dupes_stage` в тот же день: 1 254 мс на файл (2 октября — 838). Видео — в 2,4–3,5 раза быстрее.
  - dev на `big` + `big-table`, свежая база: 500 кадров — **48,0 с** с поиском («колода и стол») и 50,4 с без него;
    все 4 989 кадров — 357 с. Дубли и SHA идут только когда кадров нет (цикл `develop::spawn`).
  - Этап «Дубли» целиком: ≈ **2 860 с (47,6 мин)** на 5 000 файлов (2 053 видео, 2 943 фото, 4 стола) за вычетом
    ~200 с простоя на пересборку dev. Первые ~1 700 файлов (76 % фото) — 2,3 файла/с, хвост (половина видео) — 0,9 файла/с.
  - Зонд подвисаний (`hangprobe.ps1`, первые ~19 мин): максимум ответа окна **305 мс**, сумма задержек > 100 мс — 4,8 с.
  - `get_state` в простое — 110–200 мс (`dupes::printed` обходит набор на каждый вызов).
- **Найдено по ходу**: `get_state` падал «database is locked» — `piles::sync` писал на каждый вызов и ждал транзакцию
  Printer со сравнением внутри; сравнение вынесено из транзакции, `piles::sync` пишет только при изменениях. После
  конца отдельного поиска фон продолжал обходить внешние папки — `Scope::work` возвращает область колоды (FR-019).
- **Сверка с SC-005**: видео — выполнено (≤ 50 %); кадры с поиском не медленнее — выполнено. Целиком этап «до» на `big`
  не мерился (прогноз 29 мин был только по видео). Узкое место хвоста — фото: `Index::candidates` для фото отдаёт все
  фото набора, каждое новое сравнивается со всеми прежними (квадратично, ~4,3 млн `compare_photos` на 2 943 фото) —
  задача T044.
- **Решение после замера (T044)**: квадратичный перебор оказался дешёвым — `bench_photo_pairs` на 1 790 фото: 1,6 млн
  пар, хэш и смысл — 1,3 с. Время съедал `print::contains` (поиск кадрирования, 23 мс на пару): 8 372 вызова на
  **69 разных пар картинок** — в `big` каждое фото лежит ~11 раз (жёсткие ссылки). `contains` запоминает результат по
  хэшу байтов `look` (детерминирован — ответ бит в бит прежний, сброс после 100 000 записей): 196 с → 2,5 с, счётчики
  совпадают. В жизни помогает на копиях одного фото (бэкапы).
- **Замер после T044** (`bench_printer`, все 5 000 файлов `big` + `big-table`, по окнам из 250): **1 043 с (17,4 мин),
  209 мс на файл**; видео ~280 мс (декод 2/3, DINOv2 1/4), фото ~90 мс, сравнение ≤ 11 с на окно. Самая долгая пачка
  — 30 с (длинные видео в одной пачке): пауза и новые карты ждут конца пачки.
- **T042 (индекс по набору)** — не делается: по замеру «до» лишние записи индекса — 0,3 %.

## R-7. Оценка времени на старте (FR-004, чип «+N мин»)

- **Decision**: `dupes_estimate(scope)` → `{ files, videos, photos, minutes }`: файлы набора без готового отпечатка ×
  среднее время на видео / фото. Средние — константы из замера R-6, затем уточняются по фактической скорости этапа
  (`dupes_rate_video_ms`, `dupes_rate_photo_ms` пишутся по концу этапа). Чип скрыт, если колода не выбрана или
  всё уже отпечатано («+0 мин» не показываем).
- **Rationale**: пользователь решает по порядку величины; точность ±50 % достаточна.

## R-8. Анимация «Сито»

- **Decision**: компонент `fx/Sieve.tsx` — сетка 10×5 и SVG-дуги, только CSS-анимации (`transform`, `opacity`,
  `background`, `stroke-dashoffset`) из стенда 005; пауза — класс `paused` (`animation-play-state: paused`,
  прозрачность .5); `prefers-reduced-motion` — без анимации (неподвижный кадр). Поле `pair` из статуса удаляется —
  картинки на этапе «Дубли» больше не нужны, `named()` и `Printer.last` уходят.
- **Rationale**: живая область больше не грузит кадры с диска; анимация не зависит от данных.
